# 清单与进度

init 的全量发现与续跑、update 的影响分析、audit 的覆盖检查共用本页。Agent 选择发现方法、业务划分和分析顺序；脚本检查记录关系与指纹，不决定业务边界。清单写入仅由 init / update 执行，audit 在答复中报告新发现。

## 发现与归属

确认版本和范围，查看构建、目录、配置及业务资料，再选择搜索方法。不以单一注解、命名或目录规则作为完整发现依据。

范围内源码与配置逐文件登记。`assigned` 只表示归属确定，不代表已经阅读或验收。业务实现归属具体业务，共用组件可多归属；测试、生成代码、工具及排除项说明角色与理由。行为不明的代码保留待核对，不能因找不到调用方、代码量大或实现相似而排除。

发现入口后继续展开可执行动作：同一 Controller 的查询、保存、撤销分别处置；消息分发、任务、回调及配置选择的处理器按实际分支追踪。类名和路由前缀可辅助发现，不能用它们替代具体处理入口。入口可使用方法、函数或脚本行号定位，业务 ID 与命名由 Agent 决定。

共用逻辑可以合并编写与验收，但逐入口列明使用方、适用条件和差异，核对权限、数据操作、生效、失败和副作用确实一致。一个入口已分析不能代表整个目录；“模板同构”“都是查算写”不足以省略其他业务。

反向核对未归属文件、已归属但未追踪的业务实现、没有说明的入口、没有接收方的交接，以及涉及但未读的 SQL / 配置。业务实现中的待核对内容记入入口或单元 gaps；纯数据类型等支撑代码说明角色，按相关业务需要读取。初始化的全量范围由约定目标保持，不能通过收窄各页面深入范围消除待分析项。

收尾用不同线索反查发现结果，例如初次搜路由注解，随后查注册、调用方、配置选择与未归属实现；具体组合由 Agent 决定。同一正则重新执行只能确认可重复，不能证明无遗漏。手册自身、构建产物等在 scope.exclude 写明理由，不进入业务文件清单。

## 保存结构

清单位于 `.smart-handbook/.inventory.json`，使用[模板](../assets/inventory-template.json)与[清单 schema](../assets/inventory-schema.json)。当前格式为 V3；旧产物需要重新 init，不自动迁移。

| 字段 | 内容 |
|---|---|
| `mode` / `status` | full 或明确指定的 navigation；本次任务的 in-progress / incomplete / complete 记录 |
| `target` | commit、工作区说明和工具取得的实际时间，未知为 null |
| `scope` / `discovery` | 声明范围、排除理由、实际发现方法及尚未确认范围 |
| `files` | path、实际 SHA-256 或 null、自由文本 role、units、disposition、reason |
| `units` | id、name、entrypoints、pages、sources、depends_on、gaps |

每个入口包含 `id`、`path`、`symbol` 或 `line`、`trigger`、`status`、`claims`、`gaps`、`reviews`。ID 全库唯一；trigger 描述实际路由、订阅、事件、调度或其他调用方式。claims 引用页面 claim ID，reviews 引用 `.smart-handbook/.reviews/*.json`，不重复保存规则与验收总结。

入口状态为 pending / analysing / needs-review / accepted / known-gap。导航入口保持 pending；关键本地逻辑未查清记录 gaps，使用 known-gap。accepted 必须关联已写清的业务 claim，完成[源码复核和独立阅读](reading-review.md)，没有关键本地缺口。

单元的 sources 保存需要追踪的支撑实现、映射和配置，不等于目录内全部文件；新增发现持续补充。没有独立执行入口的公共组件由使用方的 claim 与场景复核，不虚构入口。其声明来源仍需被已验收业务的证据覆盖。

单元不手填 status / review，check 从入口、缺口和证据派生。入口 claim 来源会自动加入单元的验收证据范围，sources 只需额外登记公共实现／独立资源，不重复抄入口证据。页面复核也不在 state 中独立填写。README 使用 check 派生结果汇总，标明实际版本和未完成范围。

路径为仓库相对 POSIX 路径；来源与归属 ID 必须存在。清单允许项目需要的说明字段，但不记录凭据、敏感运行数据或仓库外路径。`scope.include` 的 `.` 仅表示全库发现，不能作为 claim 来源。

## 分批、续跑与目标变化

首轮发现就保存清单与 pending 入口，不等全量业务分析完成；后续按业务分批保存页面、入口进度、来源指纹、验收记录、缺口和下一步，再开始下一批。中断或上下文切换保持原全量目标。

已有产物时先只读 check，并核对当前发现范围。有效但未完成的 init 按入口续跑；导航完成不代表深入分析完成。已完整且指纹未变时展示记录的适用版本与阅读入口，结构通过不代表重新完成语义审计。已完成产物的代码变化提示 update；初始化仍未完成时核对变动来源及使用方，继续原 init。必需记录缺失或格式无效则重新发现与初始化；明确重建时保留已有知识和来源后核对替换。

复核实际文件版本后保存指纹。收尾重新枚举范围、核对新增/删除及分析期间变化，避免混合版本。update 只处置本次影响，未分析存量仍由 init 续跑；审计发现记录冲突时仅报告建议状态。

## 完成条件

full 保存 complete 前必须确认：

- 发现范围处理完，文件有归属或排除理由，未追踪业务实现已有处置。
- 所有纳入范围的具体入口已验收，本地接收方、状态回写与关键分支读清，没有导航入口或关键本地 gaps。
- 声明的支撑来源被业务证据覆盖；场景、独立阅读、代码定位及修订后复验记录有效。
- 页面引用、跨页交接、README 摘要与目标版本一致，通过[收尾检查](endpoint-analysis.md#收尾检查)。

远端内部实现、部署值和运行未知项单列。使核心问题无法回答的未知会阻塞验收；静态初始化不自行执行生产操作或冒充运行验证。未达到条件时继续可做的批次；只有[实际中断](workflows/init.md#持续处理清单)才提前交付，保存原因与续跑位置，保持 full / incomplete。

navigation 的 complete 仅表示声明的导航任务结束。用户明确限定范围时只报告该范围完成，不能升级成全库完成。

check 返回入口与单元派生状态、ready_to_complete、来源与验收快照变化；impact 给出来源和依赖候选及旧验收待复核项。脚本不发现未登记代码、不验证答案真假；Agent 继续负责遗漏发现与源码语义核对。
